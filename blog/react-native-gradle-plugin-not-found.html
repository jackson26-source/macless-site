Fix "Could not find react-native-gradle-plugin"

Two different-looking errors, same cause: the plugin version doesn't match the React Native you actually have installed.

Jackson · September 2026

This shows up in one of two forms, and Gradle never gets past the sync step to build anything:

Could not find com.facebook.react:react-native-gradle-plugin:0.72.0.
Searched in the following locations:
  - https://dl.google.com/dl/android/maven2/...
  - https://repo.maven.apache.org/maven2/...
Required by:
    project :

or, on a newer template:

Included build '/path/to/node_modules/@react-native/gradle-plugin'
does not exist.

Both mean the same thing. Whatever reference to the React Native Gradle Plugin (RNGP) your build is using points at something that doesn't exist for the React Native release actually sitting in your node_modules.

Why the version has to match

RNGP isn't a general-purpose Gradle plugin versioned on its own schedule. It ships inside the react-native package itself and is published in lockstep with RN core — plugin version 0.73.0 exists because RN core 0.73.0 exists, not on any independent release cadence. A build script that hardcodes a plugin version or path is really hardcoding an assumption about which RN release the project is on. That assumption is fine right up until someone runs the same script against a project one or two releases behind, at which point the plugin reference simply has nothing to resolve to.

The Maven classpath version (older templates)

Pre-0.72-era android/build.gradle files pull the plugin as an ordinary Maven dependency:

dependencies {
    classpath("com.facebook.react:react-native-gradle-plugin:0.72.0")
}

If the installed react-native version is older than the pinned number, Gradle searches Google's Maven and Maven Central, finds nothing published at that version for this project's actual toolchain, and fails before a single Java or Kotlin file compiles.

The includeBuild version (RN 0.72 and later)

Current templates don't fetch RNGP from Maven at all. settings.gradle includes it directly from the installed package:

includeBuild('../node_modules/@react-native/gradle-plugin')

The package itself was renamed at 0.72 — it used to be the unscoped react-native-gradle-plugin. A settings.gradle written for one side of that rename and run against a project on the other side references a folder that genuinely never gets created by npm install, which is exactly what "Included build ... does not exist" is reporting. It isn't a permissions or install problem — the path is just wrong for this project's RN version.

Found the hard way. Our own changelog for 2026-08-18 records live-testing the React Native variant of our Android pipeline template and hitting exactly this: the template's plugin reference didn't exist for any React Native release before 0.85, because it had been written against the newest core we'd tested and never checked against an older-but-still-supported one. It failed at the first Gradle sync, before any of the rest of the workflow ran.

The fix

Stop pinning a version or a package name at all, and let the plugin resolve from whatever React Native is actually installed. Current RN templates do this with a small Node resolution instead of a literal path:

pluginManagement { includeBuild(new File(
  providers.exec {
    workingDir(rootDir)
    commandLine("node", "--print", "require.resolve('@react-native/gradle-plugin/package.json')")
  }.standardOutput.asText.get().trim()
).getParentFile().toString()) }

If your build.gradle still carries an explicit classpath("com.facebook.react:react-native-gradle-plugin:X.X.X") line, that's usually a leftover from an older template. Modern RNGP is picked up by pluginManagement/includeBuild, so the versioned classpath entry can be removed entirely rather than kept in sync by hand.

Checking which era your project is on

Run this before touching anything:

node -p "require('react-native/package.json').version"
ls node_modules/@react-native/gradle-plugin 2>/dev/null && echo "scoped package present"
ls node_modules/react-native-gradle-plugin 2>/dev/null && echo "unscoped package present"

Whichever package actually exists on disk is the one your settings.gradle or build.gradle needs to reference. A template copied from a newer or older project is the single most common way these two get out of sync.

The pipeline resolves this by installed version, not a hardcoded one

We hit this exact class of bug live-testing our own React Native template, which is why Macless's generated Gradle config reads the plugin from your project's actual node_modules instead of a version baked in at template time.
