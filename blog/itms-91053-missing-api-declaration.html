Fix ITMS-91053: "Missing API declaration"

Apple's privacy manifest requirement rejects the upload, not the build — which is why this one blindsides people who never touched a signing setting.

Jackson · August 2026

If App Store Connect rejects your upload with ITMS-91053: Missing API declaration, the build itself succeeded. This is a separate check Apple runs against the binary after it's uploaded, looking for use of a "required reason API" that isn't declared in a privacy manifest anywhere in the app.

It trips people up in CI specifically because it often isn't caused by your code at all — it's caused by a dependency.

What a "required reason API" actually is

Since May 2024, Apple requires apps to declare why they use certain privacy-sensitive APIs, even ones that don't touch personal data in any obvious way. The most common categories that trigger this error:

  • File timestampsReading a file's creation or modification date — including from third-party libraries that log or cache to disk.
  • User defaultsUserDefaults reads/writes, including ones buried inside an SDK you didn't write.
  • Disk spaceChecking available storage before a download or cache write.
  • System boot timeUsed surprisingly often by analytics and crash-reporting SDKs for session timing.

Each category has a fixed set of Apple-approved "reason codes" (things like 1C8F.1) — you can't invent your own justification text, you pick the code that matches your actual use case from Apple's list.

Step 1: find which API and which dependency

App Store Connect's rejection email names the API category but not the source. If you built with Xcode 15+, the fastest way to find the culprit is to check whether any of your CocoaPods/SPM dependencies shipped their own PrivacyInfo.xcprivacy — most major SDKs (Firebase, Facebook SDK, most ad/analytics libraries) added these over the past year specifically because of this rule. An outdated version of a dependency is the single most common cause: the SDK itself is fine, you're just running a version from before its maintainers added the manifest.

Step 2: add or update PrivacyInfo.xcprivacy

In Xcode: File → New File → search "privacy" → App Privacy. This creates a PrivacyInfo.xcprivacy file. Inside it, under Privacy Accessed API Types, add an entry for each API category you're actually using, matching the exact key Apple defines (e.g. NSPrivacyAccessedAPICategoryUserDefaults), then pick an approved reason code under Privacy Accessed API Reasons for each one.

In a headless CI build: this file just needs to exist in your app target (or be bundled inside a framework target) before xcodebuild archive runs — there's no separate CI-specific step. If it's missing after archiving, check that the file is actually added to your target's "Copy Bundle Resources" build phase, not just sitting in the project navigator.

Why this one is worse in CI than it sounds

Locally, Xcode's own build won't flag this at all — it only surfaces as an upload-time rejection from Apple's servers, which means a CI pipeline can go green on every step (build, archive, export, upload) and still fail asynchronously a few minutes later when Apple's processing catches it. If your workflow doesn't poll for or alert on App Store Connect processing status after upload, this failure can go unnoticed for a while.

Signing Doctor won't catch this one — a build monitor will

This specific check happens after your app leaves CI, so no local tool (including Signing Doctor) can catch it before upload. The Macless pipeline polls App Store Connect after upload and surfaces rejections like this one instead of leaving you to notice a silent failure.
