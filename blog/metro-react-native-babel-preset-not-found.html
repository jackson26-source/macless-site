Fix "Couldn't find preset metro-react-native-babel-preset"

Metro fails right before the archive step, because a package that looked test-only wasn't.

Jackson · September 2026

The build has been running for a while, everything looked normal, and then it stops with:

Couldn't find preset "module:metro-react-native-babel-preset"
relative to directory "/path/to/project"

On iOS this rarely shows up on its own. It usually surfaces one step later, more confusingly, as:

error: File main.jsbundle does not exist. This must be a bug with
React Native, please report it here: ...

That second message is a red herring. Nothing is wrong with React Native. Metro never produced a bundle at all, because the very first file it tried to transform needed a Babel preset that isn't in node_modules, and an empty bundle output means the later copy step has nothing to find.

Why this fires at archive time specifically

Babel transformation isn't a test-only step. Every time Metro bundles JavaScript — the dev server, a manual react-native bundle, and critically the "Bundle React Native code and images" build phase that Xcode runs during xcodebuild archive (Android's equivalent is the bundleReleaseJsAndAssets Gradle task) — it runs your code through whatever babel.config.js specifies. If the preset named there isn't installed, the transform fails immediately, and it fails identically whether that bundle was headed for a test run or a real production archive.

How a "trimmed" scaffold does this

A stock React Native package.json keeps its Babel preset in devDependencies, sitting right next to jest and @testing-library/react-native. That's an accurate description of when it's installed, and a completely misleading one for what it's for. A setup script built to generate a lean starter project — drop the __tests__ folder, drop jest.config.js, drop anything that reads as test scaffolding — can treat the whole neighborhood of that devDependencies block as fair game and take the Babel preset with it. Nothing about where a package lives in package.json says whether the bundler needs it; devDependencies just means "not needed in the shipped app," and Metro's transform step runs long before anything ships.

Found the hard way. Our changelog for 2026-08-18 records exactly this: live-testing the React Native variant of our pipeline template, a scaffold-generation step trimmed to skip Jest also carried off a package the bundler itself depends on. It didn't surface until the archive step tried to produce the actual .ipa, several minutes into a build that had looked fine up to that point.

The fix

Reinstall the preset your project's babel.config.js actually references. Current React Native uses the scoped package:

npm install --save-dev @react-native/babel-preset

Older projects (pre-0.71-era, matching the unscoped RNGP package from the plugin-resolution post above) use the original name instead:

npm install --save-dev metro-react-native-babel-preset

Then confirm babel.config.js points at whichever one you actually installed:

module.exports = {
  presets: ['module:@react-native/babel-preset'],
};

Clear Metro's cache before the next build so a stale transform result doesn't mask whether the fix actually worked:

npx react-native start --reset-cache

The real fix is in the trimming step, not the reinstall

Reinstalling the preset gets one build working again. The structural problem is a scaffold-trimming step that decides what to remove based on which package.json block a dependency sits in, rather than whether anything in the project's actual build config — babel.config.js, metro.config.js, any Gradle or Xcode script — references it. Before any automated cleanup step deletes a "testing" dependency, it's worth actually grepping the build config for its name first.
