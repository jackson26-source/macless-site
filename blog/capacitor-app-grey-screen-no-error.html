Your Capacitor app opens to a grey screen and throws no error

A Base44 app, wrapped with Capacitor, installed from TestFlight. It opened to flat grey. No crash, no error in the console, no failed request to inspect. The web app it was built from ran perfectly in a browser.

Jackson · October 2026

A failure with no error message is a different kind of problem. There is nothing to search for.

What the grey screen actually is

It's the WebView, loaded, running, and showing you an app that rendered nothing. The shell works. Capacitor works. The app's own JavaScript is executing. It just has no data and no error to report about not having it.

That narrows things considerably. If the bundle were broken you'd get a white screen or a crash. If a request had failed you'd have a failed request. Grey with silence means the app never asked for anything.

Why it never asked

Two things, both invisible from the outside.

The app reads its own identifiers from build-time environment variables. In this case VITE_BASE44_APP_ID and VITE_BASE44_APP_BASE_URL, pulled from import.meta.env inside src/lib/app-params.js. The CI job that produced the build set neither, so the bundle shipped without knowing which app it was or where its data lived.

The API client made that worse rather than louder. It was constructed with an empty server URL, so every call resolved against a relative path. Relative is the right default for a web app served from its own domain, because /api resolves to yourdomain.com/api and everything works. Inside a native shell the page isn't served from your domain. It's served from capacitor://localhost. A relative path there resolves to a place that does not exist, and the SDK treats the result as nothing to report.

So: no app ID, no base URL, and calls pointed at a local origin with no server behind it. The app asked nobody for nothing and rendered what it had.

The fix

Three changes, none of them interesting, which is usually how this goes.

Set the environment variables in the build step that installs dependencies, before the bundle is produced. They have to be present at build time, not runtime, because the bundler inlines them.

Rewrite the API client's server URL from empty to the actual host. A one-line patch during CI is sufficient if you don't want to fork the generated code.

Enable native HTTP in the Capacitor config. This routes fetch and XHR through the native layer instead of the WebView, which also removes the CORS problem you get when a capacitor://localhost origin starts calling a real domain.

Two things learned the hard way

Use perl, not sed. The patch step originally used sed -i, which fails on macOS build runners, because BSD sed requires an argument to -i and GNU sed does not. The job did not fail loudly. It just did not patch the file. perl -pi -e behaves the same on both.

Guard the patch. A find-and-replace that silently matches nothing is worse than a build failure, because you get a green checkmark and a grey app. Follow any patch step with a grep -q for the expected result and fail the job if it isn't there. Ten seconds of config, and it turns an invisible problem into an obvious one.

The generalisable part

A failure with no error usually means the thing you expected to happen never started. Not that it started and broke. When there's nothing to debug, stop looking at the place it hurts and go one layer earlier, to whatever was supposed to kick it off.

In this case the layer earlier was a build step that set nothing, and a default that is correct everywhere except inside the one environment the app actually shipped in.
