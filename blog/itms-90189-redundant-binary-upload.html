ITMS-90189: "Redundant Binary Upload"

Two numbers, and the one that matters is the one nobody looks at. Almost exclusively a CI problem.

Jackson · September 2026
ERROR ITMS-90189: "Redundant Binary Upload. You've already uploaded
a build with build number '1' for version number '1.0'. Make sure you
increment the build string before you upload."

App Store Connect requires every upload to carry a build number it hasn't seen before for that version. You sent one it already has.

The two numbers

iOS apps carry two version strings and they do different jobs:

  • CFBundleShortVersionString — the marketing version, 1.0. Users see it. Changes rarely.
  • CFBundleVersion — the build number, 1. Users never see it. Must be unique for every single upload.

This error is about the second one. Bumping the marketing version to 1.0.1 does resolve it, but for the wrong reason — you've changed what the number is unique against rather than making the build number unique.

Why it's a CI problem specifically

Uploading from Xcode by hand, you bump the build number as part of the ritual. In CI, nobody does. The number sits in Info.plist or a build setting, checked into git, identical on every run — so the first upload succeeds and every one after fails, including a re-run of the exact same job after a flaky network failure.

That last case is the confusing one: the build genuinely uploaded the first time, the step failed later for an unrelated reason, and the retry now collides with the upload that partially succeeded.

The fix

Derive the build number from something that always increases and that you never have to think about. In GitHub Actions, that's github.run_number:

- name: Set build number from the run number
  run: |
    agvtool new-version -all ${{ github.run_number }}

It increments on every run of that workflow, forever, survives failed runs and manual re-runs, and needs no state you have to store or remember.

One sharp edge. github.run_number is per-workflow-file. Create a second workflow, or rename the file, and the counter starts again at 1 — producing this exact error on a build that "should" have a higher number than anything you've uploaded. If you split or rename a workflow, expect one collision and set an offset, or move to a scheme that can't reset.

If you're already stuck above every number you've used

Build numbers only need to be unique and increasing within a version, so you can jump. Setting the build number to a timestamp — date +%Y%m%d%H%M — steps over anything you've previously uploaded and stays monotonic. It's ugly in the build list, and it's the fastest way out of a collision when you need a release now.

Related: if the upload succeeded and the build still isn't visible to testers, the number wasn't the problem — see the build never shows up in TestFlight.
