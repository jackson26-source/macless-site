"Your app currently targets API level 35 and must target at least API level 36"

Play Console rejects the bundle after it uploads. On Capacitor, the file holding that number is regenerated on every build.

Jackson · September 2026

The upload itself works. Play chews through the bundle, shows you the size and the ABI list, and then puts a red error at the top of the release page:

Your app currently targets API level 35 and must target at
least API level 36 to ensure it is built on the latest APIs
optimized for security and performance.

You can't publish the release until that number moves. There's no override, no "I'll do it next time" checkbox.

Where the number actually lives on a Capacitor project

Not in AndroidManifest.xml, which is where most search results will send you. Capacitor puts it in android/variables.gradle:

ext {
    minSdkVersion = 23
    compileSdkVersion = 35
    targetSdkVersion = 35
    ...
}

Change both numbers to 36 and the next build targets 36. On a laptop that's the whole fix.

Why the same fix does nothing in CI

Here is the part that cost me a build cycle. If your pipeline runs npx cap add android, that command recreates the entire android/ directory from Capacitor's template every time it runs. Your edit to variables.gradle is discarded before Gradle ever sees it. The build goes green, the AAB comes out targeting 35 again, and Play rejects it again — with no indication that anything you changed was thrown away.

So the patch has to happen after the platform is generated and before Gradle runs:

- name: Target the API level Google Play requires
  run: |
    cd android
    sed -i -E "s/(compileSdkVersion|targetSdkVersion)([[:space:]]*=[[:space:]]*)[0-9]+/\\1\\236/" variables.gradle
    grep -E "(compile|target)SdkVersion" variables.gradle

That grep at the end isn't decoration. sed exits 0 whether or not it matched anything, so if a future Capacitor release renames those keys, a silent no-op sails through the build and you find out twenty minutes later from Play. I ended up turning it into a hard assertion:

for KEY in compileSdkVersion targetSdkVersion; do
  if ! grep -qE "\${KEY}[[:space:]]*=[[:space:]]*36([^0-9]|$)" variables.gradle; then
    echo "::error::Could not set \${KEY} in android/variables.gradle."
    exit 1
  fi
done

The AGP warning you'll hit next

Capacitor's pinned Android Gradle Plugin version is usually a little behind whatever API level Play has just started demanding, so bumping compileSdkVersion produces a loud warning about compiling against an untested SDK. Adding this to android/gradle.properties acknowledges it rather than leaving a scary block in every customer's build log:

android.suppressUnsupportedCompileSdk=36

You may also need the platform itself. GitHub's Ubuntu runners ship a handful of SDK platforms and not necessarily the newest one, so install it explicitly — though be warned that sdkmanager isn't on PATH there, which is its own separate afternoon.

Don't hardcode 36

Google has raised this floor roughly every August for years, and it will be 37 before long. Reading the level from a repo variable with a sane default means the next bump is a one-line change in a settings page instead of a code change:

env:
  TARGET_SDK: \${{ vars.ANDROID_TARGET_SDK || '36' }}

While you're in there: versionCode. Capacitor hardcodes versionCode 1 in android/app/build.gradle, and Play permanently refuses any versionCode it has already seen. That means a pipeline can upload exactly once — every run after the first dies at the final step, after a full build. Same fix, same reason: patch the generated file, not the repo. Tying it to the CI run number gets you a unique, increasing number for free.
