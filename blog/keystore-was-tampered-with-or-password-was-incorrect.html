Fix "keystore was tampered with, or password was incorrect"

The error text names two causes, but they're not equally likely — check the boring one first.

Jackson · August 2026

The full error from keytool (and anything that shells out to it, including Gradle's signing config and CI) looks like this:

keytool error: java.io.IOException: Keystore was tampered with,
or password was incorrect

It reads like your keystore file might be corrupted, which is alarming the first time you see it. In practice, in a CI context specifically, it's almost never actual tampering or corruption — it's a password or file problem, in that order of likelihood.

1. Check the password first — it's the cause about 90% of the time

keytool uses the same generic error message for "the file is corrupted" and "the password is wrong," which is the whole reason this error is confusing. In a headless CI job, the password almost always comes from a secret, and secrets are where small mistakes hide:

  • A trailing newline or trailing space got included when the password secret was set (very easy to do by pasting from a terminal or a password manager that appends a newline).
  • The keystore password and the key password are different values, and one got used in place of the other. A keystore generated with keytool -genkeypair without an explicit -keypass flag typically has them match — but if yours doesn't, they're two separate secrets, not one.
  • The secret simply has the wrong value in it — most commonly after rotating a keystore and forgetting to update the corresponding CI secret.

Confirm this is the cause by testing the password locally, outside of CI, against the exact same keystore file:

$ keytool -list -v -keystore release.keystore -storepass "yourpassword"

If that fails with the same error locally, it's confirmed as a password problem, not a CI-environment problem — stop looking at your workflow file and go fix the secret.

2. If the password is confirmed correct, check the file itself

This is the less common case, but it does happen — usually from how the keystore got into CI's hands in the first place, not from the keystore itself being damaged at rest:

  • Line-ending corruption. If the keystore was base64-encoded, stored as a text secret, and decoded again before use, a step somewhere in that chain (a text editor "helpfully" normalizing line endings, a shell variable losing bytes) can corrupt binary data. Keystores are binary files — they need to move through your pipeline as base64 text and back to binary exactly, never as plain text at any point.
  • An incomplete download or checkout. If the keystore is fetched from somewhere (a release artifact, an external secret store) as part of the CI job, a partial or failed fetch that doesn't hard-fail the job can leave a truncated file behind.
  • The wrong file entirely. Less embarrassing than it sounds — a debug keystore accidentally referenced instead of the release one, or an old keystore left over from before a rotation, produces exactly this error against the current password.

Quickest check: compare the file size and a checksum of the keystore in your CI job against the one you have locally (shasum release.keystore on either end). A mismatch confirms it's a transport problem, not a password problem.

Why this doesn't show up in Android Studio nearly as often

Android Studio caches keystore passwords per-project after the first successful unlock and generally reuses the same local file every time, so both of the usual CI causes — a bad secret value and a corrupted transfer — mostly don't apply locally. CI re-decodes the keystore from a secret fresh on every run with no memory of "it worked last time," which is exactly why a rotation or a copy-paste mistake surfaces here first.
