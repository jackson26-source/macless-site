Fix "No matching provisioning profiles found" in GitHub Actions

This one usually isn't about the profile at all — it's about whether Xcode is even looking at the profile you installed.

Jackson · August 2026

In Xcode's GUI, "No matching provisioning profiles found" almost always means what it says — go to the portal, fix the profile. In a headless CI build, the same message shows up for a completely different reason most of the time: xcodebuild never even looked at the profile you carefully installed, because something upstream of it is still set to automatic signing.

Check these in order — the first one catches most CI failures specifically, and it's the one Xcode's GUI never makes you think about because it handles it silently.

1. Confirm the project is actually set to manual signing for the build

If CODE_SIGN_STYLE is still Automatic in your Xcode project (the default for new projects), xcodebuild tries to manage signing itself during the build — including in CI, where there's no Apple ID session for it to manage anything with. It ignores the profile you installed into ~/Library/MobileDevice/Provisioning Profiles/ and fails with this exact error, because as far as it's concerned, there's nothing there yet.

The fix is to force manual signing at build time rather than relying on project settings, either directly on the xcodebuild command:

xcodebuild archive \
  -scheme YourApp \
  CODE_SIGN_STYLE=Manual \
  PROVISIONING_PROFILE_SPECIFIER="Your Profile Name" \
  CODE_SIGN_IDENTITY="Apple Distribution" \
  DEVELOPMENT_TEAM=XXXXXXXXXX

or via an explicit signingStyle: manual entry in the export options plist for the export step. Either way, this is the single most common cause of this error being a CI-only problem — the exact same project archives fine locally because Xcode's GUI papers over automatic signing without telling you.

2. Confirm the profile actually installed where Xcode looks

Headless CI has no Xcode session to place the profile for you — your workflow has to copy it into ~/Library/MobileDevice/Provisioning Profiles/ itself, named as <UUID>.mobileprovision. A profile sitting anywhere else, or written before the directory exists, is silently invisible to xcodebuild. Add a debug step that lists the directory right before the build:

ls -la ~/Library/MobileDevice/Provisioning\ Profiles/

If it's empty or missing your profile, the problem is earlier in the pipeline than signing — the base64 secret decoded wrong, or the copy step ran before mkdir -p created the target directory.

3. Check profile type and bundle ID match what you're building

If steps 1 and 2 check out, it's back to a real mismatch: a Development profile can't sign an Archive build meant for TestFlight, an Ad Hoc profile won't satisfy an App Store export, and the profile's App ID has to match PRODUCT_BUNDLE_IDENTIFIER exactly — a wildcard profile (com.you.*) works for basic builds but won't cover an app using push notifications or other capabilities that require an explicit App ID.

Quick sanity check if you're not sure which of the three you've hit: run security cms -D -i /path/to/profile.mobileprovision in the CI job right after installing it. It prints the profile's actual App ID, team ID, and expiry as plain XML — compare that against your build settings directly instead of guessing.

Why this trips people up more in CI than locally

Xcode's automatic signing is designed to be invisible when it works — it silently regenerates and matches profiles in the background so you never see the mechanism. CI has none of that; every piece has to be handed to it explicitly, so the first missing piece surfaces as a hard failure with a message that reads like a profile problem even when the profile was never the issue.
