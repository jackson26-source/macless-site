Fix "Version code X has already been used" on Google Play

Your CI tool can tell Play Console whatever version it wants. Play Console only believes the number actually compiled into the bundle.

Jackson · September 2026
Google Api Error: Invalid request - Version code 7 has already been used.

This lands after upload, from Google's servers, not your build tool. It means the exact versionCode embedded in the AAB or APK you just uploaded has already been published for this app, even a version you shipped weeks ago. Play Console doesn't care what version your commit message says, or what your CI dashboard says it deployed. It reads the number baked into the artifact.

Why this happens even when your tooling says the version is right

The usual setup: fastlane's upload_to_play_store action accepts a version_code parameter, so it looks like you can just increment that and move on. The catch is that parameter tells fastlane what to report, it doesn't reach into an already-built AAB and change the number compiled inside it. If your Gradle build ran with the old versionCode before fastlane ever got involved, the bundle fastlane uploads still carries the old number, whatever you pass as a parameter afterward.

This is exactly the failure documented in a real fastlane issue: fastlane correctly identified the intended new version code, but Play Console rejected the upload because the bundle itself still contained the previous one. The override happened at the wrong layer, after the artifact was already built.

The fix has to happen before the build, not at upload

The version code has to be correct in build.gradle (or wherever your Gradle config reads it from) at the moment ./gradlew bundleRelease actually runs. Two ways that reliably works in CI:

// build.gradle — read from a value CI controls before the build starts
versionCode System.getenv("BUILD_VERSION_CODE")?.toInteger() ?: 1

or, if you'd rather not touch the Gradle file at all, inject it at invocation time and make sure it lands before compilation:

./gradlew bundleRelease -PVERSION_CODE=$BUILD_VERSION_CODE

with build.gradle reading project.hasProperty('VERSION_CODE') ? VERSION_CODE.toInteger() : 1. Either way, the number has to exist before the archive step, not get patched on afterward by whatever uploads the result.

A CI guard that catches this before Play Console does

Since the bundle is the source of truth, read the version code back out of it after building and compare, instead of trusting whatever your CI thinks it set:

unzip -p app-release.aab base/manifest/AndroidManifest.xml | \
grep -a -o 'versionCode="[0-9]*"'

For an APK, aapt dump badging app-release.apk | grep versionCode does the same thing. Running this right after the build and failing loudly if it doesn't match the number you intended turns a rejected Play Console upload, discovered minutes later, into a build failure discovered immediately, with the actual mismatch printed in the log instead of a bare "already been used."

The other way this bites people

Auto-incrementing schemes that derive the version code from something that isn't monotonic across every branch (a commit count on a feature branch, a timestamp that gets reset by a rebase, a counter stored somewhere that doesn't survive a fresh CI runner) can also produce a number lower than, or equal to, one already published. The fix is the same: verify the number in the built artifact against Play Console's last known version before uploading, don't just trust that your counter always goes up.
