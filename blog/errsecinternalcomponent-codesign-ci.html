errSecInternalComponent when codesign runs in CI

It builds on your machine and dies on the runner. The certificate is there — the keychain just won’t let a headless process touch it.

Jackson · August 2026

Two error messages, one cause:

/usr/bin/codesign --force --sign ... : errSecInternalComponent
Command CodeSign failed with a nonzero exit code
User interaction is not allowed.

Neither means your certificate is missing, expired, or wrong. Both mean the same thing: the keychain holding the signing identity refused to hand it over to a process with nobody sitting in front of it.

On a Mac you own, this is invisible. macOS pops a dialog saying "codesign wants to use your keychain," you click Always Allow once, and you never think about it again. A CI runner has no screen and nobody to click. The keychain does the only thing it can — it says no.

The four things that have to be true

People usually get the first two right and stop, which is why this error is so persistent.

1. The certificate is imported with the right access

Import the .p12 into a keychain you control, and grant access to the tools that need it:

security create-keychain -p "$KEYCHAIN_PW" build.keychain
security import cert.p12 -k build.keychain -P "$P12_PW" \
  -T /usr/bin/codesign -T /usr/bin/security

The -T flags matter — without them the key exists but no binary is authorised to use it.

2. That keychain is unlocked and in the search list

security list-keychains -d user -s build.keychain
security default-keychain -s build.keychain
security unlock-keychain -p "$KEYCHAIN_PW" build.keychain
security set-keychain-settings -t 3600 -u build.keychain

set-keychain-settings is the one people skip. Without it the keychain can re-lock partway through a long build, and you get a failure that looks intermittent — same job, same code, fails sometimes.

3. The partition list is set

This is the actual fix, and it’s missing from most guides because it wasn’t needed before macOS 10.12:

security set-key-partition-list -S apple-tool:,apple:,codesign: \
  -s -k "$KEYCHAIN_PW" build.keychain

Even with -T at import time, modern macOS holds a separate ACL that decides which partitions may use the key without prompting. If that isn’t set, the prompt is still what the system wants to do — and a prompt with no one to answer it becomes errSecInternalComponent.

If you only fix one thing on this page, fix this one.

4. Signing runs as the same user that owns the keychain

Less common, but if the build shells out through sudo or a different user context, it’s looking at a different keychain entirely — one that doesn’t have your certificate in it.

To confirm it’s a keychain problem and not a certificate problem, run security find-identity -v -p codesigning in the CI job right before the build. If your identity is listed, the certificate is fine and this page applies. If it isn’t listed, the import failed and you’re looking at a different problem — start with no signing certificate found.

Why it looks intermittent

A keychain with no unlock timeout set can re-lock mid-build. The signing step that passed this morning fails this afternoon on identical code, which sends people hunting for a race condition or a flaky runner. It’s neither — it’s step 2 above.
