"sdkmanager: command not found" on GitHub Actions

Exit 127 on a line that looks fine. The more interesting question is why the identical line one step earlier reported success.

Jackson · September 2026

I added a step to install a specific SDK platform and got this:

Run sdkmanager "platforms;android-36" > /dev/null
/home/runner/work/_temp/....sh: line 1: sdkmanager: command not found
Error: Process completed with exit code 127.

sdkmanager is not on PATH on ubuntu-latest. The Android SDK is installed — $ANDROID_SDK_ROOT points at /usr/local/lib/android/sdk and the tools are all there — but the command-line tools directory isn't added to PATH, so the bare command resolves to nothing.

The part that actually matters

The step immediately above this one had been in the workflow since it was written, and looked like this:

- name: Accept Android SDK licenses
  run: yes | sdkmanager --licenses > /dev/null || true

Same missing command. Same exit 127. And that || true on the end swallowed it, so the step had been reporting success while doing absolutely nothing on every run the workflow had ever had. Months of green checkmarks on a step that never executed. The only reason I found out is that my new step called the same binary without the || true and failed loudly.

The builds still worked, incidentally — the runner image ships with the common platform licences already accepted, so nothing depended on that step succeeding. Which is exactly why nobody notices. A no-op step that guards against a problem you don't currently have looks identical to a step that works.

Finding the binary properly

It lives under $ANDROID_SDK_ROOT/cmdline-tools/<version>/bin/sdkmanager, and the version directory name isn't stable across runner images, so don't hardcode latest:

SDK_ROOT="\${ANDROID_SDK_ROOT:-$ANDROID_HOME}"

SDKMANAGER="$(command -v sdkmanager || true)"
if [ -z "$SDKMANAGER" ] && [ -d "$SDK_ROOT/cmdline-tools" ]; then
  SDKMANAGER="$(find "$SDK_ROOT/cmdline-tools" -name sdkmanager -type f 2>/dev/null | sort | tail -n 1)"
fi

if [ -z "$SDKMANAGER" ]; then
  echo "::warning::sdkmanager not found under \${SDK_ROOT}. Skipping."
  exit 0
fi

yes | "$SDKMANAGER" --licenses > /dev/null 2>&1 || true
"$SDKMANAGER" "platforms;android-36"

The command -v check first means this keeps working on any runner or container where it is on PATH. The warning-and-exit-0 fallback is deliberate: the Android Gradle plugin will usually download a missing platform itself, so a hard failure here would be worse than a note in the log.

A mistake worth repeating so you don't make it

My first version of that find was written across two lines with a backslash continuation. By the time it went through YAML block-scalar parsing and into bash -c, the continuation arrived as a literal backslash argument. find ran with no -name predicate at all, cheerfully listed every file in the SDK tree, and tail -n 1 picked an arbitrary one to try to execute:

find: '\\': No such file or directory
Using /usr/local/lib/android/sdk/cmdline-tools
/usr/local/lib/android/sdk/cmdline-tools/latest/bin/apkanalyzer
/usr/local/lib/android/sdk/cmdline-tools/latest/bin/avdmanager
...

Keep shell continuations out of YAML run: blocks. Put the command on one line even when it's ugly.

Also worth checking: build-tools

Build-tools for a brand-new API level sometimes land weeks after the platform does, so a combined install can fail on a package that doesn't exist yet. Ask for both, fall back to the platform alone — that's the part Gradle actually needs to compile against:

"$SDKMANAGER" "platforms;android-36" "build-tools;36.0.0" || "$SDKMANAGER" "platforms;android-36"

Go and grep your own workflows for || true. Every one is a step that cannot fail, which means it's a step you have no evidence works. Mine had been lying for months. The ones worth keeping are where you genuinely don't care about the outcome; the rest should fail loudly or not be there.
